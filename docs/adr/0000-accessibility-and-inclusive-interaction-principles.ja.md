# ADR-0000: アクセシビリティと包摂的インタラクションの原則

**Status:** Accepted

**Date:** 2026-08-18

## ADR-0000 の位置づけ

このADRは番号上は `ADR-0000` であるが、`ADR-0001`、`ADR-0002`、`ADR-0003` より後に採択された。

このADRは、既存ADRに記録済みの decision や invariant を遡って無効化しない。

`ADR-0000` の principle と、既存の Accepted ADR に記録された invariant が競合するように見える場合、現在の実装契約としては既存 invariant を優先する。

その競合自体は無視せず、新規 Issue または ADR update として記録し、明示的に解決する。

`ADR-0000` は、今後の設計とレビューにおけるプロダクト全体の原則を定義する。既に採択されたアーキテクチャ契約を暗黙に書き換えるものではない。

## Context

Pergamum は、小説を書く人のためのオープンソース執筆環境である。

Pergamum は Markdown を本文の保存形式として採用するが、Markdownを書くためだけのアプリではない。主目的は、作品を書くこと、長い作品を管理すること、用語や設定を扱うこと、そして作者の正本をあとから困らない形で保持することである。

そのため Pergamum は、特定の身体条件、入力環境、表示環境、IT習熟度だけを前提にしてはならない。

作者は、さまざまな環境で文章を書く。

- 日本語IME、韓国語・中国語などのIME、各国語入力
- JIS / US / ISO などのキーボード配列
- デッドキー、AltGr、OS固有の入力方式
- マウス、タッチパッド、トラックボール、カスタムポインティングデバイス
- OSのバーチャルキーボード
- スクリーンリーダー、点字ディスプレイ、音声入力、その他の支援技術
- 色覚差、視力差、運動機能差
- 低速なPC、Linux arm64、Raspberry Pi、リモートデスクトップ環境
- ITに詳しくないが、書く意思を持つユーザー

これらは「例外的な利用者」ではなく、Pergamum が文字を書くための道具である以上、最初から設計上考慮すべき利用環境である。

Pergamum は、すべての支援技術、すべての入力方式、すべてのOS・キーボード配列に対して、初期バージョンから完全な動作保証を行うものではない。

しかし、後から対応不能になる設計、特定の環境を不要に締め出す設計、見た目の都合で意味構造を失う設計は避ける。

## Decision

Pergamum は、アクセシビリティと包摂的インタラクションを、個別機能の後付け要件ではなく、プロダクト全体の設計原則として扱う。

Pergamum は、以下の原則に従う。

各原則には `P-1` から `P-8` までの安定した参照子を与える。Issue、PRレビュー、将来のADRでは、これらの参照子を使って明示的に原則を参照できる。

### P-1. 書く意思を軽く扱わない

Pergamum は、入力速度、利用できるデバイス、身体条件、視覚条件、IT習熟度の違いによって、作品を書く意思を軽く扱わない。

キーボードを高速に使えるユーザーだけを前提にしない。

マウスだけ、ポインティングデバイスだけ、OSのバーチャルキーボード、スクリーンリーダー、その他の支援技術を利用するユーザーでも、主要な操作へ到達できることを目指す。

### P-2. 主要操作を単一導線に閉じ込めない

重要な主要操作は、可能な限り複数の導線から到達できるようにする。

このADRにおける「主要操作」とは、ユーザーが作品または core project data を作成、編集、保存、開く、移動する、管理するために合理的に必要とする操作を指す。

主要操作には、アプリケーションの表示・動作状態が変化したときに、ユーザーがそれを認識し、元に戻すための操作も含む。

#### P-2a. 主要操作には複数導線を要求する

主要操作の例:

- 作品または文書を開く
- 本文を保存する
- Glossary data を作成・編集する
- 本文中の選択文字列を Glossary 登録フローへ送る
- Settings へ到達する
- 表示倍率が変わった状態から 100% に戻す

Keyboard shortcut は高速導線であり、利用の前提条件ではない。

Context Menu は文脈操作の近道として有用である。しかし、右クリック相当操作に気づかないユーザーや利用しづらいユーザーもいるため、主要操作の唯一の導線にはしない。

Command Palette は正式な探索導線として扱う。しかし、キーボード操作に強く依存するため、主要操作の唯一の導線にはしない。

「Settings へ到達する」ことは主要操作である。一方、Settings 内の個別設定項目、特に達人向け設定への到達や有効化は主要操作ではない。

#### P-2b. 高速化・探索効率のための操作は Command Palette only を許容できる

高速化、探索効率、達人向けナビゲーションを主目的とする操作は、同じ underlying outcome が別の主要導線から到達できる場合、Command Palette only であってもよい。

Command Palette only を許容できる操作の例:

- Go to Line
- prefix-based quick access
- fast heading search
- fast Glossary search

たとえば、文書を開くこと自体は主要操作であり複数導線が必要である。一方、特定の prefix を使って文書や見出しへ高速移動することは探索効率のための操作であり、同じ underlying outcome が別の主要導線から到達できるなら Command Palette only でもよい。

### P-3. 入力方式とキーボード配列を軽く扱わない

Pergamum は、IME、未確定入力、変換中の文字列、キーボード配列、デッドキー、AltGr、OS固有の入力方式を軽く扱わない。

ショートカット設計では、以下を考慮する。

- JIS / US / ISO 配列差
- Windows / macOS / Linux の修飾キー差
- IME composition 中の誤発火
- AltGr が Ctrl+Alt として解釈されうる環境
- デッドキーや記号キーの国際配列差
- ユーザーの既存の筋肉記憶

記号キーに強く依存する既定ショートカットは慎重に扱う。

配列差分により安定しない操作は、Menu、Context Menu、Command Palette など、配列に依存しにくい導線を優先する。

### P-4. 文字を画像として閉じ込めない

Pergamum は、文字を書くための道具である。

そのため、本文、用語、設定、警告、状態表示、操作名を、可能な限りテキストと意味構造として提供する。

主要な情報や操作を、画像化された文字、canvas-only UI、アイコンだけの表示に閉じ込めない。

アイコンだけのボタンには accessible name を付ける。

警告やエラーは、色やアイコンだけでなく、読み取れるテキストとして提供する。

スクリーンリーダーや支援技術から意味が失われるUIを避ける。

### P-5. 色だけで意味を伝えない

Pergamum は、色を使ってよい。

しかし、色だけを意味伝達の唯一の手段にしない。

状態、警告、エラー、保存状態、選択状態、Glossary kind、出現箇所、差分などは、色に加えて、文字、形、線種、アイコン、位置、ラベル、tooltip などを併用する。

カラーテーマは、見た目の好みだけでなく、読みやすさと識別しやすさを守るための仕組みとして扱う。

### P-6. 非ITユーザーを圧倒しない

Pergamum は、小説を書く人のための執筆環境であり、ITに詳しい人だけの道具ではない。

Settings UI は、すべての設定を初期状態で編集可能にしない。

通常ユーザーが安全に変更できる設定と、文字コード、改行コード、保存形式、診断機能などの高度な設定を分ける。

高度な設定は Settings UI 上に表示してよい。ただし、初期状態では disabled とし、編集可能にするにはユーザーが明示的に「達人向け設定」を有効化する必要がある。

「達人向け設定」を有効化するときは確認ダイアログを表示し、それらの設定が作品、語彙データ、アプリの動作に影響しうることを明示する。

警告すべき対象はユーザーの能力ではなく、設定項目の危険度である。

### P-7. 作者の正本を同意なく変えない

Pergamum は、作者の本文と語彙データを尊重する。

#### P-7a. 作者が入力した文字列を保持する

Pergamum 内で作者が入力する文字列、すなわち本文、Glossary form、Glossary description などには、不要な文字種制限、IME制御、自動正規化、自動置換をかけない。

サロゲートペア、BMP外文字、絵文字、結合文字、異体字セレクタなど、作者が意図して入力しうる正当な Unicode 文字は許容する。

#### P-7b. 外部から読み込んだバイト列は本文として扱う前に検証する

外部ファイルまたはその他の外部 source から読み込んだ byte sequence は、本文として受け入れる前に検証する。

未知encodingの生バイト列、invalid UTF、NUL文字、本文として意味を持ちにくい制御文字などは、silent に本文TEXTとして保存しない。

検証に失敗した場合は、警告、拒否、確認、退避、またはそれに類する明示的な処理を行う。

### P-8. 少数派環境を早期に切り捨てない

Pergamum は、標準的な高速PCだけを前提にしない。

Linux arm64、Raspberry Pi、リモートデスクトップ環境など、少数派・低速環境でも、可能な限り破綻しないことを目指す。

ただし、すべての環境に対する完全な性能保証を意味しない。

動作確認済み環境、既知制限、表示経路による差分は、リリースノートやドキュメントで明示する。

## Consequences

このADRにより、Pergamum のUI・コマンド・設定・表示・入力設計では以下が要求される。

### 複数導線の維持

重要な主要操作を実装する場合、Keyboard shortcut だけ、Context Menu だけ、Command Palette だけに閉じない。

例:

- 「選択範囲を用語集に登録...」は、Context Menu、Command Palette、必要に応じて Menu bar / shortcut から到達できるようにする。
- Glossary 操作や設定変更は、発見可能なUI導線を持つ。

高速化・探索効率・達人向けナビゲーションを主目的とする操作は、P-2b の定義に従って、Command Palette only を許容できる。

### Command Registry との整合

Menu、Context Menu、Command Palette、shortcut、将来のAI/automation entry point は、可能な限り同一の command semantics に接続する。

同じ操作に対して、導線ごとに別実装・別意味を作らない。

### ショートカット設計の慎重化

既定ショートカットを追加する場合、以下を確認する。

- Electron / Chromium / CodeMirror の既定処理との衝突
- OS差分
- JIS / US / ISO 配列差
- IME composition 中の挙動
- AltGr / dead key / 記号キーの扱い
- 誤爆した場合の被害

配列差分が大きいものは、既定ショートカットにせず、Command Palette / Menu / Context Menu を正式導線にする。

Shortcut customization は将来検討とするが、v0.90.0 時点では必須要件としない。

### アクセシブルなUI構造

実装時には以下を守る。

- アイコンのみのボタンに accessible name を付ける。
- 主要な入力欄には label を付ける。
- Modal / Dialog はフォーカスを適切に閉じ込め、閉じた後に元の位置へ戻す。
- Tab順を壊さない。
- 警告、エラー、状態表示を色だけで表現しない。
- 文字情報を画像だけ、canvasだけ、装飾だけに閉じ込めない。

### カラーテーマ設計

色は semantic token / CSS variable で管理し、将来の high contrast theme や色覚差分への対応を妨げない。

Glossary kind や occurrence 表示などは、色だけでなく、線種、アイコン、ラベル、tooltip などを併用する。

### Settings UI の visible but disabled 方針

Settings UI は、通常設定と達人向け設定を分ける。

通常設定では、見た目、読みやすさ、軽い操作感など、安全に変更できる項目を中心にする。

文字コード、改行コード、保存形式、診断機能、内部データ、実験的機能などは、達人向け設定として扱う。

達人向け設定は隠さない。Settings UI の下部または専用の「達人向け設定」セクションに disabled 状態で表示する。

編集可能にするには、ユーザーが「達人向け設定を有効にする」を選択する必要がある。

有効化時には確認ダイアログを表示する。

有効化状態は application-wide `settings.json` に保存する。

この状態は project data ではなく、ユーザーの環境・操作嗜好として扱う。

### 完全対応を安易に宣言しない

このADRは、Pergamum がすべての障害、すべての入力方式、すべての支援技術、すべてのOS環境に完全対応することを宣言するものではない。

対応済み範囲、未検証範囲、既知制限は、リリースノートやドキュメントで明示する。

Pergamum は、準拠レベルを安易に宣言するのではなく、検証済み環境、既知の制限、未検証範囲を公開し、ユーザーからのフィードバックを受けて段階的に改善する。

## Non-goals

このADRは、以下を即時実装範囲として要求しない。

- WCAG 2.2 AA 準拠の完全宣言
- すべてのスクリーンリーダーでの検証完了
- 点字ディスプレイ対応の保証
- すべてのIME・キーボード配列での動作保証
- Shortcut customization 機能の即時実装
- High Contrast theme の即時実装
- すべての操作に Toolbar button を用意すること
- すべての低速・少数派環境で同一性能を保証すること

ただし、これらを将来対応不能にする設計は避ける。

このADRが完全対応を宣言しない場合でも、Pergamum は何も約束しないわけではない。検証済み環境、既知の制限、未検証範囲を明示し、準拠宣言ではなく検証事実を公開する。

## Examples

### 選択範囲をGlossary登録へ送る

本文中の文字列を選択し、Glossary登録画面へ送る操作は、ショートカットだけにしない。

望ましい導線:

- Context Menu: `選択範囲を用語集に登録...`
- Command Palette: `選択範囲を用語集に登録...`
- Menu bar: 必要に応じて提供
- Keyboard shortcut: 配列差分・IME挙動を確認したうえで検討

この操作は Glossary Entry を即時作成しない。

選択文字列を canonical form の初期値として登録画面へ渡し、保存はユーザーの明示操作に委ねる。

### Zoom と表示倍率変更

表示倍率の変更は、アクセシビリティ上の補助にもなり、同時に意図しない状態変化の原因にもなりうる。

Pergamum は、Zoom / display-scale changes を、見える状態かつ回復可能な状態として扱う。

表示倍率が 100% 以外の場合、現在の表示倍率をUI上で確認できるようにし、ユーザーが明確な導線で 100% に戻せるようにする。

`Ctrl/Cmd + mouse wheel` のような利用者が学習済みの zoom input path を誤爆防止のために無効化する場合、実装Issueはその理由と代替導線を明記しなければならない。

代替導線の例:

- Menu bar からの表示倍率変更
- Status bar 上の表示倍率表示
- 100% に戻すための可視化された affordance

### 達人向け設定

通常設定では、非ITユーザーが安全に変更できる表示・操作感の設定を中心に表示する。

新規ファイルの文字コード、改行コード、保存形式、診断機能などは、達人向け設定項目として扱う。

達人向け設定は隠さない。Settings UI の下部または専用の「達人向け設定」セクションに disabled 状態で表示する。

編集可能にするには、ユーザーが「達人向け設定を有効にする」を選択する必要がある。

有効化時には、以下の確認ダイアログを表示する。

```text
達人向け設定を有効にしますか？

ここから先の項目には、文字コード、改行コード、保存形式、診断機能など、
意味が分からないまま変更すると、大切な作品や語彙データ、アプリの動作に影響する設定が含まれます。

通常は変更する必要はありません。
内容を確認し、分からない項目は変更しないでください。
```

有効化状態は application-wide `settings.json` に保存する。

この状態は project data ではなく、ユーザーの環境・操作嗜好として扱う。

### Empty State Tips

何も文書が開いていない状態では、短いTipsを表示してよい。

ただし、Tipsは画像ではなくテキストとして提供する。

Markdown記法例を出す場合も、Markdownを知らない人を置いていかない文言にする。

P-4 の悪い例:

```text
Markdown記法のチートシートを画像だけで表示する。
```

Markdownを知らない人を置いていかない文言の良い例:

```text
Markdown を知らなくても、そのまま文章を書き始められます。
```

記法をテキストで説明する良い例:

```text
行の先頭に # を置くと、見出しとして扱われます。
```

### 色覚差分

Glossary kind、警告、エラー、保存状態、選択状態などを色だけで表現しない。

悪い例:

```text
赤ならエラー、黄色なら警告、緑なら成功。
```

良い例:

```text
警告アイコン + 「警告」ラベル + 説明文 + 色。
```

## Open questions

- Shortcut customization を導入した場合、P-3 による既定ショートカットの保守性制約は緩むのか。それとも、カスタマイズ可能になっても既定ショートカットは保守的なままにするのか。
- WCAG などの完全な準拠宣言を行わない場合、Pergamum は代わりにどの検証事実を公開するのか。検証済み環境、検証済み支援技術、既知制限、未検証範囲、または別の compatibility statement を用いるのか。
- 支援技術対応の記録粒度をどの単位にするのか。release 単位、platform 単位、feature 単位、UI surface 単位のどれを採用するのか。
