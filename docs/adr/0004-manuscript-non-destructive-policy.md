# ADR-0004: 本文非破壊原則と日本語テキスト処理方針

## ステータス

Accepted

## 日付

2026-08-14

## 文脈

Pergamum は小説を書くための IDE である。

小説本文は、単なる検索対象の文字列ではない。  
本文中の文字種、記号、括弧、数詞、空白、句読点、ダッシュ、三点リーダー、波ダッシュ、表記揺れは、作者の文体・演出・時代感・組版意図・投稿先や出版社の慣習と結びつく場合がある。

そのため、一般的な業務システムや検索システムで行われるような「便利のための正規化」を、小説本文へ無条件に適用することは危険である。

例:

```text
十人十色
10人10色
一〇人一〇色
```

これらは機械的には数詞表記の揺れとして扱えるかもしれない。  
しかし文章表現としては同一ではない。

同様に、以下のような文字も、見た目が似ているからといって Pergamum が黙って置換してはならない。

```text
－
ー
―
—
─
〜
～
…
……
『』
「」
【】
```

作者が出版社の組版環境、投稿先の慣習、または自分の文体を意識して文字を選んでいる可能性がある。  
Pergamum がそれを黙って変更すると、作者の本文を破壊する。

また、日本語テキスト処理には多数の地雷がある。

```text
Unicode 正規化
濁点・半濁点の結合文字
波ダッシュ / 全角チルダ
三点リーダー / ダッシュの揺れ
半角カタカナ / 全角カタカナ
全角英数 / 半角英数
漢数字 / 算用数字
括弧の種類
踊り字
異体字
サロゲートペア
Markdown text node 分断
```

これらをすべて自動吸収しようとすると、本文の保存・検索・Preview decoration・Glossary matching・位置情報管理が複雑化し、かえって信頼できない IDE になる。

Pergamum は、本文を勝手に賢く書き換える IDE ではなく、作者の本文を尊重し、必要な検出・警告・支援を明示的に提供する IDE であるべきである。

## 決定

Pergamum は、本文を黙って書き換えない。

```text
本文は作者の正本である。
Pergamum は本文を暗黙に正規化・置換・補正しない。
```

以下を原則とする。

```text
保存本文:
  非破壊

Glossary matching:
  原則 exact match

Preview decoration:
  本文文字列を破壊しない
  表示上の装飾として扱う

Linter:
  表記揺れ・組版慣習・混在を検出する

Formatter:
  将来実装する場合も、明示的なユーザー操作によってのみ実行する

自動保存:
  正規化・表記統一・文字置換を行わない
```

Pergamum は以下を自動実行しない。

```text
Unicode 正規化による本文保存内容の変更
波ダッシュ / 全角チルダの統一
ハイフン / ダッシュ / 長音符の統一
三点リーダー / ダッシュの偶数化
半角 / 全角の統一
漢数字 / 算用数字の統一
括弧種別の統一
中黒の挿入・削除
踊り字の展開・置換
異体字の統一
```

## 設計原則

### 1. 本文は正本として扱う

Markdown 本文は作者が入力した本文そのものであり、Pergamum が勝手に変更してはならない。

```text
入力された本文
→ 可能な限りそのまま保存する
```

保存時に Pergamum が本文文字列を暗黙に書き換えることは禁止する。

### 2. 検索用の都合を本文へ持ち込まない

検索や Glossary matching の都合で文字を同一視したくなる場合がある。

例:

```text
ジャンヌ・ダルク
ジャンヌダルク

U+301C 〜
U+FF5E ～

第3騎士団
第三騎士団
```

しかし、これらを本文側で置換してはならない。

必要な場合は、将来以下のような別レイヤーで扱う。

```text
normalized shadow text
offset map
Glossary alias / variant
Linter warning
明示的な formatter
```

### 3. Glossary matching はまず exact match とする

Glossary は、登録された surface を本文中から一致検索する。

```text
登録 surface と本文 surface が一致した場合に match する
```

表記揺れを拾いたい場合は、作者が alias / variant として登録する。

例:

```text
canonical:
  ジャンヌ

alias:
  ジャンヌ・ダルク
  ジャンヌダルク
```

Pergamum は、`ジャンヌ・ダルク` と `ジャンヌダルク` を黙って同一視しない。

### 4. Boundary resolver は「誤検出抑制」であり「表記揺れ吸収」ではない

Glossary surface boundary resolver は、意図しない substring match を抑制するための機能である。

例:

```text
surface: メイド
text: オーダーメイド
```

この場合、`メイド` はカタカナ複合語の一部であり、Glossary hover が暴発するとノイズになる。  
したがって boundary resolver はこれを reject してよい。

一方で、以下のような表記揺れ吸収は boundary resolver の責務ではない。

```text
ジャンヌ・ダルク
ジャンヌダルク

〜
～

第三騎士団
第3騎士団
```

これらは alias / variant、Linter、または将来の明示的な支援機能で扱う。

### 5. Linter は警告するが、断定しすぎない

小説表現では、一般的な出版慣習から外れていることが、必ずしも誤りとは限らない。

そのため Linter は、可能な限り断定ではなく提案として表現する。

望ましい例:

```text
波ダッシュと全角チルダが混在しています。
```

```text
出版慣習では、三点リーダーを偶数個で揃えることがあります。
```

```text
同一人物と思われる表記が複数あります。
```

避ける例:

```text
波ダッシュに修正します。
```

```text
三点リーダーは誤りです。
```

```text
第3騎士団を第三騎士団に変換します。
```

### 6. Formatter は明示操作のみ

将来、表記統一や組版向け整形機能を追加する場合でも、それは明示的なユーザー操作によってのみ実行する。

```text
許可:
  ユーザーが選択して変換する
  差分 preview を出して適用する
  一括変換前に確認する

禁止:
  保存時に自動変換する
  Preview 表示時に本文を変更する
  Glossary matching のために本文を変更する
```

## 日本語処理地雷への方針

### Unicode 正規化

Pergamum は、保存本文に対して暗黙の Unicode 正規化を行わない。

```text
NFC
NFD
NFKC
NFKD
```

これらは検索や Linter の将来機能として使う可能性はあるが、本文保存時に黙って適用しない。

理由:

```text
外部エディタや Git との相互運用で大量差分が発生する可能性がある
作者が意図した文字列を変更する可能性がある
Preview decoration の offset 管理が複雑化する
```

### 波ダッシュ / 全角チルダ

以下は黙って同一視しない。

```text
U+301C 〜
U+FF5E ～
```

将来の扱い:

```text
Linter:
  混在を検出する

Formatter:
  明示操作で統一する

Glossary:
  必要なら alias / variant として登録する
```

### ダッシュ / ハイフン / 長音符

以下は黙って置換しない。

```text
-
－
ー
―
—
─
```

特に、長音符 `ー` とハイフン・ダッシュ類は意味が異なる。

例:

```text
ABC－100
ABCー100
```

見た目が似ていても、前者は型番・区切りとして、後者は長音として解釈されうる。  
Pergamum はこれらを黙って変換しない。

### 三点リーダー / ダッシュの連続

以下は Linter 領域とする。

```text
…
……
‥
――
—
―
```

出版慣習として三点リーダーやダッシュを偶数個で揃える場合があるが、Pergamum は本文を自動修正しない。

### 数詞表記

以下は黙って同一視しない。

```text
十人十色
10人10色
一〇人一〇色

第三騎士団
第3騎士団
第３騎士団
```

数詞表記は、意味・文体・慣用句・時代感と関係する。  
Glossary で拾いたい場合は alias / variant として明示登録する。

### 括弧

以下は黙って同一視しない。

```text
魔王
「魔王」
『魔王』
【魔王】
```

括弧は surface の一部として扱う。  
括弧なしでも拾いたい場合は、括弧なし surface を登録する。

### 中黒

以下は黙って同一視しない。

```text
ジャンヌ・ダルク
ジャンヌダルク
```

`ジャンヌ・ダルク` を alias として登録していても、本文の `ジャンヌダルク` には一致しない。  
必要なら `ジャンヌダルク` も alias として登録する。

将来、Linter または Glossary Editor が以下のような提案を行う可能性はある。

```text
中黒なし表記も alias に追加しますか？
```

ただし、Pergamum が黙って中黒を無視して matching することはしない。

### 踊り字

以下は文脈依存性が高いため、黙って展開・正規化しない。

```text
々
ゝ
ゞ
ヽ
ヾ
```

将来の Linter または boundary policy で扱う可能性はあるが、本文保存時に変更しない。

### 半角カタカナ / 全角英数

以下は黙って変換しない。

```text
ｵｰﾀﾞ
オーダ

Ｐｅｒｇａｍｕｍ
Pergamum
```

表記の選択が文体・演出・引用・原文再現と関係する場合がある。

## 代替手段

### 1. 自動正規化する

保存時に本文を正規化する案。

却下理由:

```text
作者の本文を破壊する
Git diff が壊れる
外部エディタとの相互運用が悪化する
組版意図を壊す可能性がある
```

### 2. Glossary matching で強い正規化を行う

検索時に、波ダッシュ、中黒、半角全角、数詞などを同一視する案。

却下理由:

```text
match range と原文 offset の対応が難しくなる
作者が意図しない hover が増える
exact match の予測可能性が下がる
boundary resolver の責務が肥大化する
```

将来、normalized shadow text と offset map を導入すれば検討可能だが、初期方針では採用しない。

### 3. Linter / alias / explicit formatter に分離する

採用。

```text
Glossary:
  exact match + alias / variant

Boundary resolver:
  明らかな substring 誤検出を抑制

Linter:
  混在・表記揺れ・出版慣習を検出

Formatter:
  明示操作でのみ本文変換
```

この分離により、本文を守りながら作者支援を追加できる。

## 結果

### 良い結果

```text
作者の本文を Pergamum が黙って壊さない
Git / 外部エディタとの相互運用を保ちやすい
Glossary matching の予測可能性が高い
日本語処理の地雷を段階的に扱える
Linter / Formatter / Glossary Editor の責務分離が明確になる
```

### 悪い結果

```text
表記揺れを自動では拾わない
alias / variant 登録の手間が増える
親切な fuzzy matching は後回しになる
一部ユーザーには「拾ってくれない」と感じられる可能性がある
```

### 受け入れる制約

Pergamum は、作者の本文を守ることを優先する。

そのため、初期段階では「便利な自動吸収」よりも「予測可能な exact match」を選ぶ。

```text
勝手に拾いすぎるより、拾う条件を作者が理解できる方がよい。
勝手に直すより、直すべきか作者が判断できる方がよい。
```
