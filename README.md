# Pergamum

[日本語](./README.md) | [English](./README.en.md)

Pergamum（ペルガモン）は、作品世界を忘れないためのオープンソース統合執筆環境です。
MITライセンスで公開しているフリーソフトウェアです。

ただし、単なるMarkdownエディタを作ろうとしているわけではありません。

小説を書いていると、本文とは別に大量の情報が発生します。

人物名。地名。組織名。固有名詞。別称。表記揺れ。時系列。人物同士の関係。ある出来事がいつ起きたのか。ある人物がその時点で何を知っていたのか。

作品が長くなるほど、それらを作者の記憶だけで維持することは難しくなります。

Pergamumは、**本文を書く場所と、作品世界について作者が知っていることを管理する場所を分け、その両方をひとつの執筆環境として扱う**ことを目指しています。

なお、Pergamumは現在まだ開発初期であり、ここで挙げている機能のすべてが実装済みというわけではありません。

ちなみにPergamumとは、現在のトルコ西部にある古代ギリシャの都市の名前です。アレクサンドリア図書館に匹敵する大図書館を擁し、羊皮紙（パーチメント）の語源にもなりました。

## なぜ作るのか

小説そのものは、ただの文章です。

だから本文はMarkdownでいい。

一方で、

> この人物にはどんな別名があるのか  
> この表記は単なる揺れなのか、それとも意図した別称なのか  
> この出来事は何年何月に起きたのか  
> この人物はこの場面の時点で、その事実を知っていたのか

といった情報は、文章だけでは扱いにくいものです。

そこを無理にMarkdownへ埋め込むのではなく、構造化されたデータとして別に持たせます。

Pergamumでは、現在その役割を次のように分けています。

```text
Markdown
    原稿本文の正本

pergamum.db
    人物・用語・時系列など
    構造化された作品情報の正本

pergamum.json
    プロジェクト設定

Assets
    画像などのバイナリデータ
```

本文をデータベースの都合に合わせることもしないし、構造化情報をMarkdownの中へ押し込むこともしません。

それぞれを、一番扱いやすい場所に置きます。

## Pergamumが目指しているもの

Pergamumが最終的にやりたいのは、作者の代わりに小説を書くことではありません。

**作者が既に決めたことを忘れないための道具**を作ることです。

たとえば、織田信長に関係する語として、

```text
織田信長
茶筅髷
吉法師
信長
お館さま
```

という文字列が本文中に現れたとします。

このうち、

- `織田信長` は人物そのもの
- `吉法師` は幼名
- `信長` は略称
- `お館さま` は立場に応じた呼称

として、文脈によって同一人物を指すことがあります。

一方、`茶筅髷` は人物ではなく髪型を表す語であり、同じ実体ではありません。

Pergamumでは、単に似た文脈に現れるからといって、文字列を勝手に同じ実体へまとめません。

さらに、同じ人物を指す文字列であっても、その意味は同じではありません。

Pergamumでは、こうした情報を単なる文字列の一覧ではなく、

```text
実体
    人物 / 地名 / 組織 / 概念 …

表層形
    正規表記 / 異表記 / 別称 …

警告方針
    警告する / 無視する …
```

という独立した軸として扱います。

また、同じ表層形が複数の実体を指すことも許します。

「武将」という語が複数の人物を指し得るなら、Pergamumは勝手に一人を選びません。

**曖昧なら、曖昧であると報告する。**

これはPergamumの重要な設計原則です。

将来的には、カクヨム・小説家になろう・アルファポリスなど、投稿先ごとに異なるルビや傍点などの記法を、同じ原稿から適切に出力することも目指しています。

## 現在の開発状況

Pergamumは現在も開発初期にあります。

現時点では、Electron上でMarkdownプロジェクトを開き、編集するための基盤に加えて、SQLiteを用いた構造化プロジェクトデータ基盤を構築しています。

Glossaryについては、

```text
Renderer
    ↓
Preload API
    ↓
IPC
    ↓
Glossary Store
    ↓
Project Database
    ↓
SQLite
```

という経路まで実装されています。

また、

- UUIDv7による永続ID
- 実体（Entity）と表層形（Form）の分離
- 曖昧一致を保持するデータモデル

まで定義・実装済みです。

ただし、Glossaryを編集するGUIはまだありません。

画面はあとから何度でも作り直せます。しかしデータ構造は何年も使われます。

そのため現在は、UIよりもアーキテクチャの整備を優先しています。

## データを失わないために

小説は、作者が何十時間、何百時間とかけて作るデータです。

そのためPergamumでは、構造化情報についても「壊れたら作り直せばいい」とは考えていません。

`pergamum.db` を構造化データの正本としつつ、将来的にはGitで差分を確認でき、人間にも読める決定論的なsnapshotを生成する予定です。

snapshotは第二の正本にはしません。

正本を二つ作ると、どちらが正しいのかという問題が必ず発生するからです。

その代わり、

```text
pergamum.db
    ↓
deterministic snapshot
    ↓
Git / backup / external tools
```

という一方向の関係にします。

snapshotから復元するときは、現在のDBを退避し、snapshot全体を検証したうえで、トランザクションを用いてデータベースを再構築する方針です。

まだ実装されていませんが、これは既にアーキテクチャ上の原則として決定しています。

## 開発について

Pergamumの開発では、設計レビューや実装支援に生成AIを活用しています。

一方、現時点のPergamum本体には、作者の原稿を生成AIへ送信したり、AIに小説本文を書かせたりする機能はありません。

AIは開発プロセスを支援するために利用しており、作者の創作そのものを置き換えることは目的としていません。

## インストール

Pergamumは現在開発中であり、一般利用向けの配布物はまだありません。

現時点では、ソースコードから開発環境を構築して試すことができます。

```bash
npm install
npm run dev
```

## 設計について

Pergamumでは、大きな設計判断をADR（Architecture Decision Record）として残しています。

コードだけを見ると、

> なぜUUIDv7なのか  
> なぜGlossaryの表記を別テーブルにしたのか  
> なぜSQLiteが正本なのか  
> なぜsnapshotを正本にしないのか

といった理由は時間とともに失われます。

そのため、「何を採用したか」だけでなく、**何を検討し、なぜ採用しなかったのか**もできるだけ記録しています。

現在の主要なADR:

- [ADR-0001: Project Persistence Architecture](./docs/adr/0001-project-persistence-architecture.md)
- [ADR-0002: Structured Project Data and Glossary Model](./docs/adr/0002-structured-project-data-and-glossary-model.md)

実装より先に設計を決めることもあります。

あとで安く直せるコードより、あとで高くつくデータ構造を先に決めたいからです。
